Why HoneyBan

HoneyBan is an alternative to fail2ban and UFW. It uses eBPF and XDP to block bad traffic deep inside the kernel—so it's faster and more efficient.

eBPF + XDP

Packet filtering runs in the kernel with eBPF and XDP (eXpress Data Path). No userspace round-trips for every packet.

~10× faster

Kernel-level blocking means less overhead than traditional tools. More packets per second, lower CPU.

Kernel-level

Blocks before packets hit the full network stack. Same idea as fail2ban/UFW, but deeper and faster.

Comparison: UFW vs fail2ban vs HoneyBan

Same goal — block attackers and bad IPs. All three tools enforce firewall rules; HoneyBan does it at kernel level with eBPF/XDP for higher speed and lower CPU.

Criteria UFW fail2ban HoneyBan
Where blocking happens Userspace → iptables/nftables Userspace → parses logs, then iptables Kernel (XDP, driver level)
Blocking speed After packet crosses stack After logs + rule update ~10× faster — drop at NIC
CPU overhead Medium — netfilter per packet Higher — log parsing + rule changes Lower — early drop, less work
Packet path NIC → stack → netfilter → drop NIC → stack → app → logs → iptables NIC → XDP → drop (short path)
Rule type Static (admin-defined) Dynamic (from log patterns) Dynamic (daemon + block list)

How each tool works

UFW

Algorithm: Front-end for iptables/nftables. You define rules (allow/deny by port, IP, interface). Rules are static; the kernel applies them in the netfilter stack after the packet has been processed by the network stack.

Packets follow the full path: NIC → kernel stack → netfilter hooks → accept/drop. No automatic reaction to log events; you add/remove rules manually or via scripts.

fail2ban

Algorithm: Monitors log files (e.g. SSH, Apache) for patterns (e.g. failed logins). When a pattern matches, it runs an action (usually add an iptables/nftables rule to block that IP). So blocking is reactive and happens in userspace after log parsing.

Packet path for blocked IPs: packet still enters the stack and is then dropped by iptables. fail2ban does not see packets directly; it only reacts to what applications write to logs.

HoneyBan

Algorithm: Uses eBPF programs attached at the XDP hook (earliest point in the kernel for packet processing). A block list (IPs/CIDRs) is maintained; the XDP program checks each packet’s source IP against this list and drops matching packets before they enter the rest of the stack.

Packet path: NIC → driver → XDP program → drop (or pass). No userspace round-trip per packet; the block list is updated by a daemon and reflected into the eBPF map used by the XDP program.
